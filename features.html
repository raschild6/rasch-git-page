Virtualized Commit Graph

Smooth scrolling through huge histories, with your stashes and uncommitted work right in the graph.

  • Branches as coloured lanes that stay narrow: a merged branch frees its column. Labels marked local, remote or both (↑ / ↓ / ✓).
  • Only the visible rows are drawn and history loads in pages: huge repositories scroll smoothly.
  • Uncommitted work (WIP) and every stash appear as nodes in the graph.
  • Right-click labels and commits to check out, merge, rebase, reset, cherry-pick, tag and more; select several commits at once.

The graph draws branches as coloured lanes and merges as curves; a branch keeps one colour and one column for its whole life, and once it is merged its column is free for the next branch, so a history of many short branches stays narrow and main stays a straight line, and labels each branch tip as local, remote, or both (↑ / ↓ / ✓), in the colour of its line. Only the rows near the visible area are materialized, and history loads in pages as you scroll, so repositories with very long histories open fast and scroll smoothly.

Uncommitted changes appear as a "WIP" node, and each stash appears as its own node attached to the commit it was taken from. The columns (branch, graph, message, author, date) fit the window, and you can resize them. With the graph focused, ↑ / ↓ step from commit to commit and the view follows.

The graph is also where you act on history, with right-click menus:

  • Branch and tag labels: double-click one to check it out (the same safe checkout as the menu); right-click to check out, merge into the current branch, fast-forward, rebase, push, pull, rename or delete a local branch (remote labels: check out, track, merge, delete on the remote; tags: check out, push, delete; a tag that is only on the remote: fetch it, or delete it there).
    • Fast-forward in both directions: on main, a right-click on dev offers Fast-forward 'main' to 'dev' and Fast-forward 'dev' to 'main': the second moves dev up to main without leaving main (only offered when it really is a fast-forward).
    • Reset Soft / Mixed / Hard to here on another branch's label or on a remote label (e.g. origin/feature) moves the branch you are on to it: useful to make a local branch match its remote.
  • A commit (its row or its coloured dot): cherry-pick, revert, Reset Soft / Mixed / Hard to here (soft keeps the differences staged, mixed keeps them unstaged, hard discards them after a confirmation; only when a branch is checked out, and undoable), create a branch or tag there, copy the SHA.
    • Several commits at once: Ctrl+click (Cmd+click on macOS) adds or removes a commit, Shift+click or Shift+↑ / ↓ selects a range. Right-click one of them (or any branch / tag label while several are selected) → Cherry-pick N Commits (No Commit) applies them all, oldest first, in one go; or copy their SHAs. Branches on These Commits acts on the branches labelled on the selected commits: pull, push, merge into the current branch, delete them locally, on the remote or both (deletions ask first; the checked-out branch is left out), with the same progress, cancel and summary report as Manage Branches.
    • Create Tag has a multi-line message box and Load from File…: pick your release notes (e.g. docs/releases/v1.0.3.txt), edit them if needed, then Create or Create & Push. Lines starting with # are left out, as in Git.
  • A stash node: apply, pop or drop it.

Where to find it

The center of each repository tab; right-click a branch / tag label or a commit's dot.

Why it's different

  • Typical Git GUIs build every row of the history up front, which gets slow on large repositories.
  • Stashes and work in progress usually live in a separate list; here they are part of the history view.
  • The graph can optionally show tags (a per-repository setting) and marks a detached HEAD explicitly.
  • Labels in the colour of their history line: branch and tag labels are drawn in the colour of the line their commit sits on, so you see at once which branch owns which part of the history. A mark at the start of the label, on a small filled block, says where each one is: ✓ here and on the remote, ↑ only here (not pushed yet, or ahead), ↓ only on the remote, and a red ≠ when the remote has a different tag with that name. Tags have a dashed border, branches a solid one; the checked-out branch is the only label filled with its colour, so you find it at a glance. The remote's tag list is read along with the fetches you already do (and remembered across restarts), never while you scroll.
  • Branch and commit actions are one right-click away on the graph itself, instead of in separate dialogs or menus.

Find any loaded commit by message, author or hash, instantly.

Deep Search

Find any file — or any line of code — across every branch and the whole history.

  • File names across the whole history, with globs.
  • Text at the tip of all branches: where is this still used?
  • Text in history: when was this added, and when removed?
  • Runs in the background, results as they arrive, cancellable.

One window, three searches (it reopens on the one you used last):

  • File names — type a file name, part of it, or a glob (*.sql, src/**/test_*.py); optionally limit how many commits to search and a date range. Results list every commit that added, modified, renamed or deleted a matching file, with hash, date, author and message. Click one and the graph jumps to that commit — loading older history if needed — while the diff viewer shows that file's changes.
  • Text in branches — "where is parse_config still used?": every line containing a text or a regular expression at the tip of all your branches (local and remote), only the local ones, or the current one. Results are grouped by file, with the line number, the match highlighted and the branches that have that line ("main +3") — the same line on many branches is one row, not one per branch. Double-click a line to open the blame of that file, at that branch, on that line.
  • Text in history — "when was OLD_API_KEY added, and when was it removed?": the commits that added or removed a piece of text, even in files deleted long ago, or (option) every commit whose changed lines match a regular expression. Each result shows whether the text was added or removed, with the matching line; click it to see the commit and the file's diff.

The text searches have Regex, Match case, Whole word (branches) and an In files filter (src/**/*.py, *.md). Right-click a result for File History, Blame or Show in Graph. Every search runs in the background with a progress bar, shows results as they arrive and can be cancelled. Text searches look at committed content.

Where to find it

Edit → Deep Search… (Ctrl+Shift+F).

Blame & File History

Who changed each line and why — and every version of a file, renames included.

  • Blame: author, date and commit next to each block of lines, shaded by age.
  • Step back past a commit with Blame Previous Version.
  • File History: every commit that changed a file, across renames, ready to restore.
  • Blame shows the file with a gutter of author, date and commit next to each block of lines, shaded by age (newer is warmer).   • Many Git GUIs offer blame as a plain, separate window or not at all; here it sits in the main view, linked to the graph and the commit details.
  • File History follows renames and shows each change inline, without a terminal git log --follow -p.

Smart Diff Views

Hunk, Inline or Split — one click to switch, with syntax highlighting and search; changed images compared before / after; Edit Here turns the diff into an editor for a quick fix.

  • Hunk, Inline or Split views, syntax highlighting for 24 languages.
  • Edit Here: fix a file right in the diff, encoding and line endings kept.
  • Image diff: side by side, swipe, onion skin and pixel difference.
  • An open diff updates by itself when the file changes.
  • Three views: Hunk shows only the changed blocks, Inline shows the whole file with changes in place, and Split shows old and new side by side with aligned rows.
  • Readability: syntax highlighting for 24 languages (Python, JavaScript, TypeScript, Java, C/C++, C#, Go, Rust, Kotlin, Swift, Ruby, PHP, SQL, HTML, CSS, JSON, YAML, TOML, XML, Markdown, INI / .env, Dockerfile, Makefile, shell), a minimap of changes, and Ctrl+F search inside the diff.
  • Clean copy: copied code has no + / - prefixes, so it can be pasted straight into an editor.
  • Always current: an open diff updates by itself. A working-tree or staged diff shows the file's new state after a pull, a reset or a change made elsewhere (scroll position kept), and closes when the file has no changes left; a commit's diff opened on a branch tip follows that branch when a fetch or pull brings a newer commit that changes the file.

Edit Here. Fix a file without switching to an IDE. Right-click a changed file → Edit Here, press Edit in the diff (Ctrl+E), or right-click a line → Edit Here at Line N: the diff turns into an editor at that line, highlighted.

  • Save with Ctrl+S: the changes lists update straight away, and back in the diff (Esc or a click on Hunk / Inline / Split) you see your new change at the line you were on.
  • The file stays as it was in every other respect: encoding (UTF-8, UTF-16, with or without BOM, Latin-1), line endings (LF, CRLF, CR) and the executable bit.
  • Find (Ctrl+F), go to line (Ctrl+G, Cmd+L on macOS), word wrap, auto-indent, line numbers and the same syntax colours as the diff; files up to 10 MB (highlighting up to 2 MB).
  • Nothing is lost by accident: switching file, closing the tab or quitting asks to save, and so does a git operation (stage, commit, checkout…) while edits are unsaved. If another program changes the file, the editor reloads it, or asks when you have unsaved edits.

Image diff. Click a changed image (PNG, JPEG, GIF, BMP, WebP, ICO, SVG, TIFF where supported) — in the working tree, the staged changes, a commit or a stash — and see it before and after, right in the app:

  • Side by side with size and file size ("Before 640×480 · 34 KB"), zoom and scrolling kept in step;
  • Swipe: a slider shows the old version on one side of the line and the new one on the other;
  • Onion skin: fade the new version over the old one;
  • Difference: the changed pixels highlighted over a dimmed image, with how many changed ("1,234 pixels changed (3.2 %)") — or "No visible change" when only the file's metadata differs.

Fit, 100 % (real pixels, also on high-resolution screens), zoom buttons and the mouse wheel; a checkerboard, theme, black or white background behind transparent pixels; added and deleted images shown on their own; during a conflict, ours next to theirs.

From the page you can Stage, Unstage or Discard (asks first) the image, copy it, open the old or new version in an external program, and for SVG switch to the text diff of its source. Very large images ask before loading and show a scaled preview; View → Image Diff turns it off.

Where to find it

Click a changed file in the right panel, or a file of a commit; the view switcher is in the diff header. Images open in the image page (modes in its toolbar; View → Image Diff to turn it off).

Why it's different

  • Most Git GUIs offer one diff layout, or at most two.
  • Hunk-level staging works straight from the diff (see Hunk-level staging).
  • Most Git GUIs send you to an external editor for any change; here a one-line fix happens where you are reading the diff, and the diff is one key away.
  • Most Git GUIs show "binary file changed" for an image, or the two versions without a way to tell what moved; here four views, including a pixel-exact difference with a count.

Hunk-Level Staging

Stage or unstage individual hunks right from the diff.

  • Stage, unstage or discard a file, a hunk, or a selection of files.
  • Stash one file or only the selected ones.
  • Moved and renamed files are one row, with only the real changes.
  • Flat list or folder tree, remembered per repository.
  • Files: stage, unstage or discard a single file with the buttons that appear when you hover it, or everything at once with Stage All / Unstage All. Discarding a file takes two clicks: the first turns the red arrow into a red bin, the second discards; clicking elsewhere or waiting a few seconds cancels it.
  • Several files at once: Ctrl+click (Cmd+click on macOS) and Shift+click select several files, in the unstaged list, the staged list or both together. Right-click the selection to Stash Selected (only those files, staged and unstaged changes alike, new files too; everything else stays exactly as it is), Stage Selected / Unstage Selected (files already on that side are skipped), Discard Selected… (asks first, listing the files; one Undo brings them all back) or Diff Selected (the first diff, with ‹ / › arrows to step through the others). Popping that stash in the app brings the files back as they were, staged parts staged.
  • Stash one file: right-click a single file and choose Stash This File…. Stashing one file or a selection first asks for the stash message, pre-filled with Git's usual one (WIP on main: …) so you can keep it or write your own; Cancel stashes nothing.
  • Room for either list: drag the line between Unstaged Files and Staged Files to give one list more space; either can shrink down to just its header, so both headers always stay visible. Double-click the line for half and half; the position is remembered.
  • Hunks: in the diff, stage or discard a single hunk of an unstaged file (discard asks first, reverts only that hunk and can be undone), or unstage a single hunk of a staged one.
  • Fallbacks: when Git's standard patch application can't handle a hunk (for example, new files or unusual line endings), the app falls back to its own blob-level staging so the action still works.
  • Views: changed files can be shown as a flat list or as a folder tree, remembered per repository for the unstaged and staged lists.
  • Moved and renamed files: a file you move to another folder or rename (in the file manager, your editor or with git mv) is one row, R, with where it came from next to its name in grey (← src/old/), in both lists: before staging too, where Git itself still sees a deleted file and a new one. Its diff starts with "Moved src/old/ → src/new/" and shows only what changed inside the file, or "No content changes" for a plain move. Stage, unstage, discard and stash take both sides of the move together; the commit details show renames the same way. Files with accented or non-Latin names work everywhere too.

Where to find it

The right panel (Unstaged / Staged files) and the diff viewer.

Why it's different

  • Partial staging is often missing or fragile in simpler GUIs; here it is built to work on edge cases.
  • Stash just a few files, even across the staged and unstaged lists, without disturbing the rest, and the stash holds only those files (Git's own partial stash also records everything else that was staged).
  • Every discard can be undone (see Undo / Redo).
  • Most Git GUIs show a moved file as a deletion plus a new file until both are staged, and a staged move as a whole new file; here it is one row with only its real changes, before and after staging.

Commit Templates

Pre-filled commit titles with your project's version and branch.

  • Predefined commit titles with {version}, {branch} and {issue}.
  • The version is read from the right file for about 50 kinds of projects.
  • The first template fills the title for you; a counter warns past 72 characters.

You keep a list of predefined commit titles with placeholders: {version} is the project's version and {branch} is the current branch. The version is read from the right place for about 50 kinds of projects — package.json, pyproject.toml, Cargo.toml, pom.xml, Gradle, .csproj, a Helm chart's appVersion, pubspec.yaml, CMake, a VERSION file and many more — skipping the traps (a dependency's version, the Node or SDK version, the chart's own version).

On a branch linked to an issue, {issue} (#123) and {issue_title} are filled in too.

The first template pre-fills the commit title automatically and keeps it up to date when you change the version, until you type your own title; the sparkle button next to the title offers the others. The title field shows a character counter that warns before you pass 72 characters. You can amend the previous commit, or commit and push in one click.

Where to find it

The Commit box in the right panel; edit the list in Edit → Commit Messages…; choose the version's source in Repository → Version Source….

Review Before Commit

Merges and cherry-picks are staged for review — never committed behind your back.

  • Merges and cherry-picks stop with the changes staged and the message pre-filled.
  • Review, adjust, then Commit; Abort discards it.
  • Several commits can be cherry-picked together, oldest first.
  • "Already up to date" merges never make an empty commit.

Merging a branch or cherry-picking a commit applies the changes to the staging area with the commit message pre-filled, and stops there. You review the result, adjust it if needed, and press Commit when you're happy; Abort Merge discards it. A merge that would change nothing ("already up to date") is detected and reported instead of producing an empty merge commit.

Several commits can be cherry-picked together (select them with Ctrl+click or Shift+click): they are applied oldest first and their changes add up in the changes panel, still without a commit. If local changes would get in the way, the app says which files before touching anything.

If a commit conflicts, the conflict editor opens and Continue Cherry-pick goes on with the commits still to apply (the panel says which commit stopped and how many are left), while Abort puts back exactly what was there before, including changes you had already staged.

Where to find it

Right-click a branch → Merge; right-click a commit → Cherry-pick; select several commits, then right-click one → Cherry-pick N Commits (No Commit).

Why it's different

  • Most GUIs merge and cherry-pick straight into a commit, and you notice problems afterwards.
  • Here nothing lands in history until you have looked at it.

Conflict Resolution

Resolve conflicts line by line, and never lose local changes when switching branches.

  • Merge, pull, rebase, cherry-pick and revert conflicts open a three-pane editor (ours, theirs, result).
  • Take whole hunks or single lines from either side.
  • Use all ours / theirs in one click; Save & Mark Resolved when done.
  • Where it opens: when a merge, pull, rebase, cherry-pick or revert produces conflicts, the tab switches to conflict mode — a list of conflicted and resolved files, plus a three-pane editor (ours, theirs and the result).
  • Resolving: take a whole hunk from either side with a checkbox, or single lines with +/−, and the result builds in the order you pick. Use all ours / theirs is one click, and Save & Mark Resolved marks the file done.
  • Finishing: Esc pauses conflict mode and you can resume it from the changes panel; Continue and Abort finish or cancel the operation.
  • Auto-stash: checking out a branch with uncommitted changes carries them across, using the stash only when the new branch touches the same files; changes that conflict with the new branch stay in the stash until you choose to resolve them.

Where to find it

Opens automatically in the repository tab when a conflict happens.

Why it's different

  • Many GUIs hand conflicts to an external merge tool, or only offer "use mine / use theirs" per file.
  • Here resolution is built in and works line by line, and it can be paused.
  • Safe checkout means switching branches never requires a manual stash.

Safe Checkout

Never lose local changes when switching branches.

  • Uncommitted changes come with you, staged and unstaged as they were.
  • A branch behind its remote can be brought up to date in the same step: you are asked first.
  • On conflict nothing is half applied: your changes stay safe in the stash.

Checking out a branch with uncommitted changes carries them across, staged and unstaged as they were; they go through the stash only when the new branch touches the same files. If the branch's remote has new commits, you choose whether to bring it up to date in the same step, and the graph scrolls to the branch you switched to.

  • Nothing half applied: if your changes conflict with the new branch, the working tree stays clean and the changes stay in the stash. Apply them and resolve the conflicts, switch back to the previous branch with them, or keep them for later.
  • Checkout and pull in one, if you want: when a branch is only behind its remote branch, the app asks Checkout & Pull, Checkout Only or Cancel before doing anything; the pull is a fast-forward with the commits already fetched. Edit → Pull on Checkout makes it always or never pull. If both sides have new commits, you choose Merge, Rebase or Cancel, as with Pull.
  • Branch names that already exist: Create Branch checks the name as you type (also names that differ only in upper / lower case, which clash on macOS and Windows). An existing branch is never moved behind your back: check it out, move it to the chosen commit (confirmed and undoable) or pick another name. A name that exists only on the remote offers to track it.
  • Stashes too: applying or popping a stash is all or nothing; while you resolve its conflicts a popped stash leaves the list, and Abort puts it back untouched.

Where to find it

Automatic whenever you check out a branch.

Why it's different

  • Safe checkout means switching branches never requires a manual stash, or a separate pull to catch up with the remote.
  • Your changes are always in one place: the stash or your files, never both.

Undo / Redo

Undo commits, checkouts, resets, discards, stashes and more — safely.

  • Undo commits, checkouts, resets, discards, stashes, rebases, pulls, tags and bulk actions.
  • Undoing a commit puts the changes and the message back.
